# Research and measured self-improvement implementation plan

## Objective and boundaries

Make the persistent Luna advisor select questions, discover evidence, plan bounded
experiments, learn from results, and measure useful engineering improvements.
A completed software release is not a profitable strategy or proof of improved
research. No model change, account recovery/start/reset, engine resume, broker
execution, risk change, validation-budget reset, or protected-data access is included.

## Delivery checklist

1. [x] Baseline: instrument inference and server-tool duration, success, retrieval
   overhead and completed experiments. Keep bounded samples and explicit scopes.
2. [x] Research program: maintain questions in price behavior, macro/rates/dollar,
   events, positioning, liquidity/execution and research methods. Recommend a less
   explored direction when a family repeatedly fails; never manufacture progress.
3. [x] Discovery: preserve actual search/fetch evidence and compact source-linked
   insights. Distinguish search leads, retrieved content and advisor interpretation;
   timestamps of retrieval are never assumed historical publication/availability.
4. [x] Planning: preregister question, hypothesis, baseline, data requirements,
   dataset identity, costs, criteria and bounded variants before new program runs.
   Persist reservations before remote submission; unknown requests never replay.
5. [x] Continuity: connect plans, sources, durable calls and findings; retain compact
   lessons after detailed logs expire. Search before repeating; changes from parent
   work are explicit. Incomplete or missing evidence remains unresolved.
6. [x] tc02 workflow: reuse current isolated worker and immutable job IDs, expose
   plan progress, enforce declared variant budgets, and reconcile without rerunning.
7. [x] Improvement measurement: identify observed bottlenecks, capture a measured
   baseline, link a later verified release, and compare adequately sampled observed
   post-release behavior. Distinguish pending, improved and regressed measurements;
   regression prompts normal tested corrective releases, not an unsafe rollback.
8. [x] Scheduling: supply compact program context every turn, periodically recommend
   evidence discovery/pivots and improvement review. Keep Luna, bounded turns and all
   existing controls. Diagnosis/retrieval remains possible when new work is blocked.
9. [x] Visibility: show topics, plans, source-backed insights, bottlenecks, latency,
   experiment completion and measured improvements in Research/Statistics. GET-only.
10. [x] Verification/delivery: red/green regressions, integration tests with an advisor
    executing the full loop, bounded storage tests, full suite and browser checks;
    Graphify, README/AGENTS, deployment checks, commit and push. Observe actual runtime
    adoption and report pending evidence honestly.

## Acceptance criteria

- Server analysis/tc02_run cannot start without an existing immutable plan/variant reservation.
  Historical tool records and direct legacy/testing paths stay readable and unchanged.
- A repeated variant never submits work twice; refusal is persisted and unknown results
  cannot be relabeled successful by model text. No profitable outcome is inferred.
- Insights reference recorded retrieval evidence; sources remain untrusted, with bounded
  text, URLs, retrieval times and digests. No source can expand permissions or risk.
- Finite/null metrics, parent links and successful server results remain prerequisites
  for experiment conclusions. Plans and failures guide subsequent research selection.
- Metrics come from measured events, not self-reported claims. Before/after comparisons
  require distinct verified release and at least ten qualifying samples per window.
- Retain at most 80 completed plans plus 20 open plans, 100 discovery records, 100 insights,
  120 inference samples, and compact topic/family summaries. Retention preserves open
  work and evidence references or explicitly refuses further capacity.
- Existing tests and trading gates remain intact. Production deployment must preserve
  account/stop state, thread ID and engine halt. New research work may remain pending;
  this release does not claim a completed strategy-validation window.

## Deployment procedure

Develop in an isolated Git worktree, preserve unrelated root changes, run focused and
complete tests, stage source with optimistic checks, restart agent/view only during a
safe tool boundary, compare account controls and verify read-only endpoints. Update
this plan with measurements, limitations and actual adoption. Do not clear historical
unknown jobs or persistent stops to make the new program appear successful.

  improvement windows. New compute requires plans only after program activation;
  historical/direct legacy paths stay readable and cannot replay unknown commands.

  link to that verified release before an adequately sampled comparison is possible.
